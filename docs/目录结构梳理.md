### 1.2 代码层：两条互不相交的支线

根目录 10 个 `.py` 全部平铺，没有包结构，但实际上分成清晰的两组：

**本地支线**（`segment.py` 为中心，2 个脚本依赖）
`scan.py`（增量扫描调度）、`check.py`（逐字校验）。这一组是**可运行的生产流水线**。

两组共用同一批输入 `.txt`，但不共享任何代码，也不共享输出命名约定。
`segment.py` 既是库又是入口，`ds_client.py` 是纯库，其余 8 个是纯入口。

## 二、问题清单（按代价排序）

### P0 — `ds_client.py:24` 硬编码了真实 API 密钥

```python
KEY = os.environ.get("DS_KEY", "<一条 68 字符的真实网关密钥，此处不复制>")
```

这条密钥已经进入 git 历史（`8283655` 起），从仓库当前状态删掉它**不能**让它失效。

处置顺序不能颠倒：
1. **先去网关后台吊销 / 轮换这条密钥** —— 这一步做完之前，其他步骤都是安全剧场；
2. 再把默认值改成必填：`KEY = os.environ["DS_KEY"]`，缺失时直接报错；
3. 历史清洗（`git filter-repo` 或重建仓库）视这个仓库是否会公开而定，密钥吊销后优先级不高。

### P1 — 271 MB 数据入库，其中约 176 MB 是纯冗余

三处冗余都是可验证的，不是估算：

**(a) `.json` 与 `.raw.json` 内容完全相同 —— 43 MB**
逐篇 `json.load` 后对象相等，只是缩进不同。同一份数据存了两遍。

**(b) `_接口返回/` 里 96% 是「处理中」的轮询响应 —— 约 50 MB**
801 个 `query.response.json` 中，770 个是 690 字节的状态轮询（中位数就是 690），
只有 30 个大于 100 KB —— 而那 30 个正是最终结果，与同名 `.json` 再次重复。
换句话说这 52 MB 里，有用的信息量约等于 25 个 `submit.response.json`（几 KB）。

**(c) `.segments.json` 与 `.json` 高度重叠 —— 81 MB**
`.segments.json` 是 `.json` 里 `result.utterances` 的重排版本，外加 `audio_url` 等 6 个头字段。
它是唯一带独立结构价值的派生文件，但没必要同时保留 `.json` + `.raw.json` + 它三份。

建议（三选一，从保守到激进）：
- **保守**：删 `.raw.json`（43 MB）和 `_接口返回/` 里的非最终轮询响应（50 MB），立省 93 MB，不损失任何信息；
- **中等**：再只保留 `.json` 与 `.segments.json` 其中之一，省到约 140 MB；
- **激进**：数据整体移出仓库（对象存储 / git-annex / 本地目录），仓库只留 `.txt` + `.task.json` 约 2 MB，
  用 `SERMON_SRC` 指过去 —— 这也正好是 `scan.py` 当初的设计意图（见 P2）。

无论选哪条，**已入库的 271 MB 在 `.git` 里仍占 38 MB**，只有重写历史才能回收。

### P2 — `scan.py` 的源目录写死为仓库外的 Windows 绝对路径

```python
SRC_DIR = os.environ.get("SERMON_SRC", r"C:\Users\23695\Documents\ChatGPT\讲道录音识别\识别结果\豆包2.0")
```

仓库里明明有同名同内容的 `识别结果/豆包2.0/`，但默认值指向别处。
在任何非该台 Windows 机器上，`python scan.py --once` 开箱即扫空目录。
建议默认值改为仓库内相对路径 `os.path.join(HERE, "识别结果", "豆包2.0")`，
`SERMON_SRC` 保留为覆盖手段（数据外移后正好用得上）。

### P3 — 命名不一致，导致 3/32 篇讲道对扫描器不可见

`scan.py` 的文件名正则是：

```python
PATTERN = re.compile(r"^GH_约伯记\d+章\d+到\d+节_热词识别\.txt$")
```

实测 32 个正文 `.txt` 里命中 29 个，漏掉 3 个：

| 漏掉的文件 | 原因 |
| --- | --- |
| `GH_伯1章1到8节20260104_热词识别.txt` | 用简称「伯」+ 日期后缀，不符合 `约伯记\d+章` |
| `GH_约伯记6章28节到7章2节_热词识别.txt` | 跨章范围，`\d+章\d+到\d+节` 表达不了 |
| `约伯记首段60秒_热词测试.txt` | 测试文件，可接受被跳过 |

前两个是真实讲道内容被静默跳过，不报错也不记日志。
第一个还引出一处历史遗留：`output/` 里 `GH_伯1章1到8节20260104_热词识别.txt` 和
`GH_约伯记1章1到8节_热词识别.txt` 是 md5 完全相同的同一篇，说明当时是靠手工改名绕过这个正则的。

建议把正则放宽到 `^GH_.*_热词识别\.txt$`，并在 `one_round` 里对「命中正则但内容为空」
之外的跳过也打一行日志，避免再出现静默丢篇。

### P4 — `__pycache__/` 被提交入库

7 个 `.cpython-314.pyc` 在版本控制下，且绑定 CPython 3.14。**本次已处置**（见第四节）。

### P5 — `output/` 一个目录混了三类东西

41 个文件，语义上是三类，靠文件名前缀隐式区分：

- **输入副本**：`GH_*.txt`（3 个）—— 本该在 `识别结果/` 里，出现在 output 是手工改名的残留；
- **人工 gold**：`gold.md`、`gold_v2.md` —— 评测基准，**是这个目录里最有价值、最该长期保留的东西**，
  却和一次性实验产物混在一起；
- **实验产物**：`ab1_` `full1_` `noise1_` `noise2_` `temp0_` `sum1_` `trial1_` `v2` `v3_low_`
  `v3_none_` `v4_none_` `v5_low_` `v5_none_` `raw_response` 等 tag 前缀（共 13 组）。

建议拆成 `output/`（可随时删的产物，整个目录进 `.gitignore`）+ `gold/`（入库，人工基准）
+ 输入副本归位。这样「哪些能删」就不再需要靠记忆判断。

### P6 — `probe/` 无人引用、无说明

`p1.json`~`p4.json` 是 4 个手写的最小请求体（`{"model":..., "messages":[{"role":"user","content":"hi"}]}`），
`grep -rn probe *.py` 无命中。是当初手工 `curl` 探接口留下的。
建议要么加一行 README 说明它是干什么的，要么删掉 —— `raw_call.py` 已经覆盖了同样的用途。

## 三、建议的目标结构

如果要动手重排，推荐下面这个形态。它把「两条支线」显式化，并把可删的和不可删的分开：

```
BibleRag/
├── README.md  .gitignore  requirements.txt
├── docs/
├── biblerag/                    # 包化，消灭平铺 import
│   ├── ds_client.py             # 远程支线公共库
│   ├── prompts/                 # prompts_v5.py 及后续版本
│   └── segment.py               # 本地支线公共库
├── scripts/                     # 8 个命令行入口
│   ├── scan.py  check.py
│   └── trial.py  compare.py  noise.py  v3.py  goldeval.py  raw_call.py
├── gold/                        # ★ 入库：人工评测基准（原 output/gold*.md）
├── data/                        # gitignore：识别结果软链或本地副本
├── output/                      # gitignore：实验产物
├── logs/  state/                # gitignore：运行时
└── tests/                       # 目前为零，见下
```

改动代价：8 个入口脚本的 import 需要从 `import ds_client` 改成 `from biblerag import ds_client`
（或加一个 `setup.py`/`pyproject.toml` 做 editable 安装）。10 个文件的规模，一次做完约半小时。

**顺带一提**：仓库现在没有任何测试，而 `ds_client.py` 里的行号覆盖校验
（完整覆盖、不重叠、不越界、拼回逐字相同）恰好是最适合写单测的纯函数逻辑 ——
不依赖网络，输入输出都是结构化数据。这是目前性价比最高的一块空白。
